# DEC-0056: Baseline version-sync and TEST_COMMAND bootstrap contract

- Date: 2026-03-24
- Status: Accepted
- Story: `US-0074`
- Research refs: `R-0051` (including post-discovery findings 2026-03-24)
- Related: `DEC-0046` (runbook command bootstrap), `US-0063`, `US-0016`, `US-0018`,
  `US-0057`, `US-0073` / `DEC-0055` (installer parity and scratchpad materialization)

## Context

Baseline validation (`tests/run-tests.ps1`, `tests/run-tests.sh`) enforces four
deterministic checks that were failing independently of in-scope sprint work:
Homebrew stable formula alignment with npm, and installer/CLI materialization of
`TEST_COMMAND` in `docs/engineering/runbook.md` for detectable stacks. Operators
need a single architecture contract so execute/QA can fix root causes without
widening scope or masking failures.

## Decision

### 1. Canonical version source (npm)

1. **`package.json` `version`** is the **only** authoritative semantic version
   for repository baseline sync assertions and for deriving GitHub release tag
   segments used in packaging.
2. **Homebrew stable formula** (`packaging/homebrew/its-magic.rb`) **must** be
   updated in lockstep with any `package.json` version change that is meant to
   ship: the committed formula is part of the same release surface as npm.
3. **Release automation** (`scripts/release-all*.ps1`, `npm run release:brew-only`,
   etc.) remains the operational backstop so the formula cannot lag npm without
   an explicit, reviewed exception (not used for routine releases).

### 2. Homebrew formula invariants (baseline + real installs)

For the stable formula checked into this repo:

1. **`url`** must include the tarball path matching the npm/Git tag convention
   `v{package.json.version}.tar.gz` (same `version` string as `package.json`,
   including prerelease segments when present).
2. **Ruby `version`** must equal **`package.json` `version`** as a literal string
   (Homebrew’s formula `version` field, not only the URL).
3. **`sha256`** must match the published tarball for that tag at release time;
   placeholder or stale checksums are a defect for consumers and for reproducible
   CI/brew flows.
4. **Regression tests** continue to assert literals derived from
   `package.json` against `its-magic.rb`; no bypass or relaxed grep for “close
   enough” versions.

### 3. TEST_COMMAND bootstrap (installer + CLI + runbook)

1. **Owning surfaces**: `installer.ps1`, `installer.sh`, `installer.py`,
   `bin/its-magic.js` (delegation paths), materialized
   `docs/engineering/runbook.md` (from `template/` on install), active +
   `template/` runbook parity — aligned with `DEC-0046` precedence
   (`user override > detected defaults > fail-fast diagnostics`).
2. **Baseline-assert contract** (until explicitly widened by a future decision):
   after bootstrap on detectable stacks, the materialized runbook’s
   **`TEST_COMMAND`** line must resolve to **only**:
   - `npm run test`, **or**
   - `sh tests/run-tests.sh`
   (exactly as asserted by the consolidated test scripts; PowerShell
   `tests/run-tests.ps1` is **not** a baseline-eligible emitted value for this
   contract — see §4.)
3. **Detector ordering** must remain **cross-platform consistent**: prefer
   `npm run test` when `package.json` declares a non-empty `scripts.test`; when
   npm is not the chosen path and a POSIX shell runner is appropriate, prefer
   `sh tests/run-tests.sh` when present — matching `installer.sh` behavior and
   avoiding Windows-only branches that emit disallowed values.
4. **Non-destructive reruns**: pre-existing non-empty `TEST_COMMAND` in user
   runbook is not silently overwritten; mismatches are failures for tests and
   QA, not masked defaults.
5. **Triple installer + CLI parity**: the same logical bootstrap outcome for a
   given target environment class across `installer.ps1`, `installer.sh`,
   `installer.py`, and CLI-spawned install paths (`US-0074` `AC-5`, `AC-8`).

### 4. PowerShell test runner and future widening

Emitting `tests/run-tests.ps1` as `TEST_COMMAND` may be valid for local Windows
workflows but **violates** the current baseline assert set. Any product intent to
treat the PowerShell runner as first-class bootstrap output requires a **scoped**
follow-up (decision + test contract change), not a silent installer change —
per `R-0051` remediation tradeoff analysis.

### 5. Parity and documentation

Active repo and `template/` must stay aligned for formula, installers, runbook
bootstrap behavior, and test scripts (`US-0074` `AC-8`). Operator-facing
remediation for version drift and bootstrap regressions is documented in
`docs/engineering/architecture.md` (**US-0074**) and this decision.

## Consequences

- Execute work for `US-0074` has explicit acceptance targets: formula literals
  and `TEST_COMMAND` lines must satisfy §2–§3 without weakening asserts.
- Release discipline must treat Homebrew as a first-class artifact in the same
  change set as npm version bumps when both channels ship.
- If teams later adopt PowerShell-first bootstrap, they must update baseline
  tests and record a new decision — not override `DEC-0056` implicitly.

## Options considered

1. **Widen baseline tests to accept `tests/run-tests.ps1` immediately** —
   Rejected for `US-0074` architecture baseline; reserved for an explicit
   follow-up if Windows-first bootstrap becomes product intent (`R-0051`).
2. **Formula-only patches without npm canonical discipline** — Rejected;
   reintroduces drift and false greens on one channel only.
3. **Lock formula + bootstrap contracts to `package.json` and baseline-allowed
   `TEST_COMMAND` values (chosen)** — Matches research, tests, and parity goals.
