# DEC-0019: Release Gate Ordering and Mandatory Evidence Model

## Status

Accepted

## Context

US-0039 requires release readiness tightening so `/release` can proceed only
after mandatory check-in tests, QA completion, and UAT completion evidence pass
in deterministic order. Current release guidance already contains UAT gating but
does not fully codify mandatory ordered test + QA + UAT evidence with a strict
default no-bypass contract.

## Decision Drivers

- Enforce deterministic release gate order with clear fail reasons.
- Require auditable evidence pointers per gate verdict.
- Preserve existing UAT completeness contract while adding missing gates.
- Prevent silent bypass by default while keeping explicit escalation path.
- Keep optional runbook commands optional (avoid false failures).

## Options Considered

### Option 1: Keep current UAT-only release gate

- **Description**: Continue with only UAT completeness as hard gate.
- **Pros**: Minimal changes to release flow.
- **Cons**: Missing explicit test and QA readiness enforcement.

### Option 2: Single aggregated "quality pass/fail" gate

- **Description**: One combined gate for tests + QA + UAT.
- **Pros**: Shorter gate expression.
- **Cons**: Reduced diagnosability and non-deterministic failure attribution.

### Option 3: Deterministic ordered mandatory gates (chosen)

- **Description**: Apply strict gate order:
  check-in tests -> QA -> UAT -> release notes/runbook updates.
- **Pros**: Clear sequencing, deterministic remediation, stronger auditability.
- **Cons**: Requires structured gate evidence records.

### Option 4: Allow default soft bypass with warning

- **Description**: Warnings for failed/missing gates but allow release continue.
- **Pros**: Faster release throughput under pressure.
- **Cons**: Contradicts mandatory gate intent and increases production risk.

## Decision

Adopt Option 3.

Define `/release` readiness as a strict ordered gate chain:

1. Check-in test evidence gate (mandatory baseline `TEST_COMMAND` evidence).
2. QA completion gate (no unresolved blocking findings).
3. UAT completion gate (verified/populated, no unresolved fail state).
4. Only after all pass, proceed to release-note/runbook finalization.

Default bypass is disallowed. Any exception requires an explicit decision gate
with documented rationale and traceable decision reference.

## Rationale

Ordered mandatory gates reduce ambiguity and eliminate "partial readiness"
interpretations at release time. Per-gate verdict logging provides auditability,
supports QA regression coverage, and gives actionable operator guidance for
remediation. The model preserves compatibility with current projects where
optional lint/typecheck commands are blank, since mandatory gating remains
test + QA + UAT only.

## Override evidence contract (US-0039)

When a release override is used (release despite a failed gate), the following must be recorded:

- **Decision record**: Reference to this DEC or a new DEC that authorizes the override.
- **Rationale**: Documented reason (e.g. accepted risk, one-time waiver).
- **Approver**: Who approved the override.
- **Risk acceptance**: Explicit statement of risk and any follow-up conditions.

Evidence must appear in `sprints/Sxxxx/release-findings.md` and queue `gate_snapshot`; reason code `RELEASE_GATE_OVERRIDE_APPROVED` with pointer to decision record.

## Consequences

### Positive

- Deterministic release behavior and stronger readiness discipline.
- Clear evidence contract for TL/QA/release handoff traceability.
- Lower risk of shipping with unresolved quality blockers.

### Negative

- Additional release metadata/reporting burden.
- Teams need clear freshness criteria for "latest check-in test" evidence.

### Neutral / Follow-up

- Override path remains possible but explicitly escalated through decision gates.
- QA should add positive/negative and stale-evidence scenarios for each gate.
