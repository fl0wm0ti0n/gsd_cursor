# DEC-0011: Research Entry Format and Knowledge Base Structure

## Status: Accepted

## Context

US-0029 introduces structured research entries that agents can cross-reference
by ID. The `/research` command, PO agent (during `/intake`), and Tech Lead
agent (during `/architecture`) all produce research output that needs to be
persistable, referenceable, and maintainable.

The format must balance structure (for cross-agent referencing) with flexibility
(research is varied — some findings are rich with multiple sources, others are
"I checked and found nothing relevant").

## Options

### Option A: Strict entries with all fields required

Every research entry must have: ID, date, topic, query, sources (URLs),
findings, linked story/decision IDs, confidence level, and status.

- Pros: maximum consistency, every entry is fully self-documenting.
- Cons: high friction for lightweight research ("checked, nothing found"). Many
  fields would be filled with "N/A" or left empty, undermining the strictness.
  Agents may skip research to avoid the overhead.

### Option B: Semi-structured entries with minimal required fields

R-xxxx ID format. Required fields: id, date, topic. Optional fields: query,
sources, findings, linked stories/decisions, confidence (default: medium),
status (default: current).

- Pros: IDs enable cross-referencing ("per R-0003"). Minimal required fields
  keep entry creation lightweight. Optional fields add value when available
  without blocking creation. Status field enables knowledge freshness tracking.
- Cons: entries may vary in completeness. Some may be sparse.

### Option C: Free-form prose with section headers (no IDs)

Keep `docs/engineering/research.md` as narrative sections. No entry IDs, no
structured fields.

- Pros: zero overhead, natural writing.
- Cons: no cross-referencing capability — agents can't say "per R-0001" in
  decisions or handoffs. No freshness tracking. Harder for the curator to
  maintain (which sections are current vs outdated?).

## Decision

**Option B is accepted.** Semi-structured entries with the R-xxxx ID format.

### Entry schema

```markdown
## R-xxxx

- **Date**: YYYY-MM-DD
- **Topic**: [short description]
- **Query**: [search query or research question, optional]
- **Sources**: [URLs or references, optional]
- **Findings**: [summary of what was found]
- **Linked**: [US-xxxx, DEC-xxxx references, optional]
- **Confidence**: [high/medium/low, default: medium]
- **Status**: [current/outdated/superseded, default: current]
```

### Required vs optional fields

| Field | Required | Default | Purpose |
|-------|----------|---------|---------|
| ID (R-xxxx) | Yes | Auto-increment | Cross-referencing |
| Date | Yes | — | Freshness tracking |
| Topic | Yes | — | Discoverability |
| Query | No | — | Reproducibility |
| Sources | No | — | Verification |
| Findings | No | — | Knowledge content |
| Linked | No | — | Traceability to stories/decisions |
| Confidence | No | medium | Trust calibration |
| Status | No | current | Knowledge freshness |

### Status lifecycle

- **current**: findings are believed to be accurate and relevant.
- **outdated**: sources or context have changed; findings may no longer apply.
- **superseded**: a newer entry (referenced by ID) replaces this one.

Curator manages status transitions during `/refresh-context`.

## Consequences

- All agents can reference research by ID in decisions, architecture, and
  handoffs (e.g., "per R-0003, the library supports...").
- Entry creation is lightweight — only 3 fields required. Agents won't skip
  research to avoid format overhead.
- Curator has structured metadata (date, status) for freshness management.
- Entries may vary in completeness, which is acceptable — sparse entries are
  better than no entries.
- The format extends naturally to the existing `docs/engineering/research.md`
  file, which currently contains free-form content.
