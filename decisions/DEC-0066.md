# DEC-0066: Deterministic installer completeness contract for `missing`/`upgrade` (BUG-0003)

- Date: 2026-03-31
- Status: Accepted
- Bug: `BUG-0003`
- Research: `R-0061`
- Supersedes: none

## Context

`BUG-0003` confirms a real install completeness gap: framework-critical scripts can still be absent after `missing` and `upgrade` flows, even when installer branch logic is parity-aligned across `installer.ps1`, `installer.sh`, and `installer.py`. `R-0061` isolates root cause to required-path inventory drift (manifest omission), not mode-branch divergence. We need the smallest enforceable contract that prevents silent partial installs while preserving existing install mode semantics and backlog status authority (`US-0045`).

## Options considered

1. **Keep current behavior + docs reminder only** - Rejected: non-deterministic, allows silent misses to recur.
2. **Hard-code required scripts in each installer** - Rejected: highest parity drift risk (three implementations + template mirrors).
3. **Manifest-only required inventory + post-install validator (chosen)** - Keep one source of truth in `installer-owned-paths.manifest`, add deterministic completeness verification, and enforce parity tests.

## Decision

### 1. Required script inventory contract (normative)

- `docs/engineering/context/installer-owned-paths.manifest` is the sole required-script inventory for installer-owned framework scripts in install completeness checks.
- `scripts/enforce-triad-hot-surface.py` MUST be present in the manifest install include set and governed by paired clean ownership policy.
- No second implicit inventory source (glob-derived or hard-coded fallback) is allowed.

### 2. Mode semantics remain unchanged

- `missing` and `upgrade` branch behaviors remain as implemented; this decision does not alter skip/overwrite classification rules.
- Completeness enforcement is a post-install invariant check over required script inventory, not a replacement for mode branching.

### 3. Deterministic completeness diagnostics

- Install completion MUST verify that all required manifest scripts exist at expected paths after copy/classification logic runs.
- Missing required entries MUST fail closed with deterministic reason codes:
  - `INSTALL_COMPLETENESS_FAILED`
  - `INSTALL_REQUIRED_SCRIPT_MISSING:<path>`
- Diagnostics MUST include remediation that points to manifest parity and rerun guidance.

### 4. Parity implementation strategy

- Preferred implementation path: shared validator utility in Python (`installer.py`) with shell wrappers (`installer.ps1`, `installer.sh`) reusing the same result contract to avoid semantic drift.
- If wrapper-local checks are unavoidable, they MUST match the Python reason-code contract exactly.

### 5. Test and parity strategy (normative)

Implementation MUST include deterministic coverage for:

- `missing` mode positive case: required scripts present after install.
- `upgrade` mode positive case: required scripts present after install and user-data rules preserved.
- negative case: missing required script in staged input triggers `INSTALL_REQUIRED_SCRIPT_MISSING:<path>`.
- active + `template/` parity validation for installer entrypoints, manifest, and related tests.
- clean/install symmetry check for newly required script paths.

### 6. Scope boundary

- This decision addresses installer completeness for framework-owned scripts only.
- It does not redefine runtime orchestration policy, release gates, or bug lifecycle status authority.

## Consequences

- Installer runs gain deterministic proof of required script presence, reducing trust gaps in packaged or upgrade scenarios.
- Manifest governance becomes more explicit: additions/removals require paired install + clean review and parity tests.
- Sprint work is straightforward and bounded (manifest update, validator path, deterministic tests).

## Risks

| Risk | Mitigation |
|------|------------|
| Manifest remains incomplete for future scripts | Enforce required-inventory review in parity tests and install regression checks. |
| Cross-installer drift in diagnostics | Centralize validator contract in Python and reuse from wrappers. |
| Over-strict blocking in customized repos | Keep enforcement scoped to installer-owned framework paths only. |
| Install/clean asymmetry for new required paths | Pair manifest install and clean policy checks in the same test matrix. |

## Decision outcome

- Approved option: **3** (manifest-authoritative required inventory + deterministic completeness validator)
