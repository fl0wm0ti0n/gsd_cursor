# DEC-0014: Compatibility Change Propagation Model

## Status: Accepted

## Context

US-0034 requires API/contract changes to be surfaced to dependent
repos/components so agents can derive required follow-up tasks and gate release
when risk is critical. The model must remain process-level, lightweight, and
non-blocking by default.

The user asked specifically for API changes to be visible to dependent
repos/components.

## Options

### Option A: Manual narrative updates only

Track compatibility changes in free-form notes and handoffs.

- Pros: minimal structure; quick to write.
- Cons: low determinism; inconsistent impact coverage; hard for agents to derive
  tasks or gate decisions reproducibly.

### Option B: Contract diff signal with impacted consumer list

Record each contract change as a structured signal including change type,
severity, and impacted consumers from compatibility links.

- Pros: deterministic propagation; easy task derivation; clear severity-based
  gate policy.
- Cons: requires manifest link accuracy and a lightweight signal format.

### Option C: Full automated dependency graph and CI orchestration

Implement dynamic graph analysis and automated cross-repo pipeline orchestration.

- Pros: high automation potential.
- Cons: exceeds story boundary (tooling/runtime orchestration); higher
  complexity than needed for workflow-level observability.

## Decision

**Option B is accepted.** Use structured contract-change signals with impacted
consumer lists and severity.

Canonical artifacts:
- `docs/engineering/compatibility-signals.md`
- `docs/engineering/compatibility-report.md`

Signal minimum fields:
- `signal_id`, `story_id`, `contract_id`, producer, from/to version,
  `change_type`, `impacted_consumers[]`, `severity`, `required_actions[]`,
  `status`.

Gate rule:
- Decision gate triggers before release only when observability is enabled and
  unresolved critical compatibility findings exist.

## Consequences

- Agents can derive follow-up work for each impacted consumer deterministically.
- QA and release gain evidence-based compatibility visibility.
- Drift between API docs and contract artifacts can be tracked as low/medium
  findings instead of hidden assumptions.
- No default overhead when `CROSS_REPO_OBSERVABILITY=0`.
