# Decision DEC-0003

Status: Accepted

## Context

US-0018 requires a smart upgrade mode for the installer. Three design questions need answering:

1. How should `upgrade` be exposed in the CLI?
2. How should files be classified (framework vs. user-data)?
3. How should version tracking work in target repos?

## Options

### CLI exposure

1. **Option A: `--mode upgrade` as 4th mode value** — fits the existing `--mode missing|overwrite|interactive` pattern.
2. **Option B: Separate `--upgrade` flag** — independent of `--mode`, could conflict with existing modes.
3. **Option C: Auto-detect** — if `.its-magic-version` exists, automatically use upgrade logic regardless of mode.

### File classification

1. **Option A: Path-pattern lists in installers** — two hardcoded lists (`FRAMEWORK_PATHS`, `USER_DATA_PATHS`) in each installer. Simple, no external file, but must be kept in sync across 3 installers.
2. **Option B: JSON manifest file** — a `template/.its-magic-manifest.json` listing every file with its category. Single source of truth, but sh installer has no JSON parser without external tools.
3. **Option C: Directory convention** — classify entire directories (e.g. `.cursor/commands/` = framework, `docs/` = user-data). Coarse but simple.

### Version tracking

1. **Option A: `.its-magic-version` file** — simple text file in target repo root containing the version string. Easy to read/write in all 3 languages.
2. **Option B: Entry in target's package.json** — only works if target has a package.json.
3. **Option C: Hidden metadata in an existing file** — fragile, parser-dependent.

## Recommendation

- CLI: **Option A** (`--mode upgrade`). Cleanest fit with existing pattern. Discoverable in `--help`. No flag conflicts.
- Classification: **Option A** (path-pattern lists). Directory-level patterns are sufficient for all 86 files. Avoids JSON parsing in sh. The patterns are stable and rarely change. The duplication across 3 installers is acceptable given the patterns are simple lists.
- Version tracking: **Option A** (`.its-magic-version` file). Universal, zero-dependency, works in every installer language.

## Impact

- `bin/its-magic.js`: add `upgrade` to mode validation.
- `installer.ps1`, `installer.sh`, `installer.py`: add `FRAMEWORK_PATHS` / `USER_DATA_PATHS` lists and upgrade branch in the copy loop.
- Template: no changes needed (classification is by path, not per-file metadata).
- Tests: add upgrade scenario to test runners.
