# DEC-0018: Sync Policy Control Model and Guarded Auto-Push Semantics

## Status

Accepted

## Context

US-0038 requires configurable sync cadence with safe defaults, mandatory test
checks before push, QA-first constraints for feature work, branch safety, and
deterministic observability. Current workflow supports manual validate-and-push
scripts, but lacks a formal phase-triggered policy model and common reason-code
contract for sync decisions.

## Decision Drivers

- Preserve non-disruptive default behavior for existing manual teams.
- Enable configurable automation without bypassing QA quality boundaries.
- Make push eligibility deterministic and auditable.
- Keep implementation process-level (no runtime git orchestration engine).
- Maintain parity expectations across active/template behavior docs.

## Options Considered

### Option 1: Always auto-push at every phase boundary

- **Description**: Any completed phase auto-triggers push when checks pass.
- **Pros**: Simple cadence; frequent remote sync.
- **Cons**: Unsafe for feature work pre-QA; too disruptive by default; weak
  branch safety guarantees.

### Option 2: Manual-only sync model

- **Description**: Keep only user-invoked sync, no policy-driven auto behavior.
- **Pros**: Safest operationally; zero extra policy complexity.
- **Cons**: Does not satisfy requested configurable cadence and phase triggers.

### Option 3: Policy-driven guarded auto-sync (chosen)

- **Description**: Introduce a canonical mode model
  (`disabled|manual|by_phase|by_milestone|custom_phase_list`) plus guarded
  eligibility checks for any auto-push attempt.
- **Pros**: Meets requested configurability with safe defaults; deterministic
  pre-push gating and branch constraints; compatible with existing manual flow.
- **Cons**: Requires explicit policy/evidence vocabulary and artifact logging.

### Option 4: Delegate all gating to CI only

- **Description**: Allow local auto-push freely and rely on CI to reject bad
  pushes.
- **Pros**: Minimal local policy logic.
- **Cons**: Violates mandatory local test-before-push requirement and does not
  satisfy pre-QA auto-push prohibition intent.

## Decision

Adopt Option 3.

Define a policy-controlled sync model with default non-auto behavior and a
guarded auto-push eligibility chain:

1. Evaluate only at phase-completion boundaries.
2. Require trigger match for configured mode.
3. Require explicit auto-push enablement.
4. Enforce QA-first restriction (no feature auto-push before QA pass).
5. Enforce branch safety deny-by-default for protected/default branches unless
   explicitly allowlisted.
6. Enforce mandatory pre-push checks with `TEST_COMMAND` baseline and optional
   lint/typecheck when configured.
7. Emit deterministic sync verdict with reason code and evidence references.

## Rationale

This model balances safety and flexibility:
- It preserves current manual behavior by default (near-zero overhead).
- It allows teams to opt into cadence-based automation without relaxing core
  safeguards.
- It keeps branch governance explicit and fail-closed.
- It provides clear evidence for QA/TL/release traceability and post-mortem
  analysis.

## Consequences

### Positive

- Deterministic sync behavior across phases and milestones.
- Strong protection against premature or unsafe auto-push events.
- Shared reason-code contract improves debugging and QA verification.
- Aligns with existing validate-and-push script baseline.

### Negative

- More artifact/reporting fields to maintain.
- Teams enabling auto-push must define and maintain branch allowlists.
- Additional documentation alignment required in active/template copies.

### Neutral / Follow-up

- Optional check behavior depends on runbook command population.
- Sprint implementation should include regression cases for disabled/manual,
  pre-QA denial, branch denial, and check-failure paths.
