# DEC-0013: Manifest Topology and Ownership Model

## Status: Accepted

## Context

US-0034 requires compatibility observability across multiple repositories and
components with concrete ownership and contract metadata. The architecture needs
both global visibility (what exists and how systems depend on each other) and
local ownership (what each repo/component actually publishes and consumes).

The user additionally requested per-repo and per-component manifests so each
repository can describe its own APIs and changes while still enabling cross-repo
impact analysis.

## Options

### Option A: Global manifest only

Use one central manifest for all repos, components, and contracts.

- Pros: one place to read and update; easy global search.
- Cons: weak local ownership; high edit contention; stale risk increases because
  component owners must update a remote central artifact for every change.

### Option B: Local manifests only

Each repo/component owns only local manifests; no global registry.

- Pros: ownership is clear and close to code; low central coordination.
- Cons: no canonical cross-repo inventory; impact analysis requires expensive
  discovery each time; harder to produce consistent compatibility reports.

### Option C: Hybrid model (global registry + local manifests)

Maintain a global registry for inventory and compatibility links, while each
repo/component maintains local manifests for contracts, versions, and ownership.

- Pros: combines global visibility with local ownership; deterministic impact
  traversal; aligns with per-repo/per-component requirement.
- Cons: two artifact layers to keep aligned; requires curation discipline.

## Decision

**Option C is accepted.** Use a hybrid manifest topology:
- Global registry in `docs/engineering/manifests/registry.manifest.yaml`
- Local repo manifest in `docs/engineering/manifests/repo.manifest.yaml`
- Local component manifests in
  `docs/engineering/manifests/components/<component_id>.manifest.yaml`

Ownership model:
- Repo/component owners update local manifests.
- Tech Lead maintains cross-repo link intent during architecture.
- Curator validates global/local alignment during `/refresh-context`.

## Consequences

- Compatibility analysis becomes deterministic: contract changes can traverse
  global links to impacted consumers.
- Planning and QA gain concrete inputs for multi-repo impact tasks.
- Additional maintenance exists, but only when optional mode is enabled.
- Default-off behavior is preserved via `CROSS_REPO_OBSERVABILITY=0`.
