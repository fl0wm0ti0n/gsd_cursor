# DEC-0012: Security Review Integration Model

## Status: Accepted

## Context

US-0028 adds an optional security and compliance review capability to the
workflow. The fundamental question is how to integrate security review into the
existing agent architecture: as a new dedicated agent role, as augmented
behavior on existing agents, or as a standalone command without agent backing.

The framework currently has 6 agent roles (PO, Tech Lead, Dev, QA, Release,
Curator). Security review needs to operate at two workflow points: post-
architecture (design review) and post-execute (code review).

## Options

### Option A: New 7th agent role (`security.mdc`) with dedicated command

A dedicated security agent definition with its own persona, inputs, outputs,
and `/security-review` command. Activated by scratchpad flags. When disabled,
the agent and command are never invoked — zero overhead.

- Pros: clean separation of concerns. Security expertise is a distinct "hat."
  Follows the established one-role-per-agent pattern. Flag-controlled activation
  means existing workflows are untouched. Agent has focused context (security
  knowledge, compliance profiles) without dilution from other concerns.
- Cons: one more agent file to maintain. Adds a phase step to the workflow
  (when enabled). Template parity requires new files.

### Option B: Security "mode" augmenting Tech Lead and QA

Add security review behavior to Tech Lead (for design review) and QA (for code
review) when `SECURITY_REVIEW=1`. No new agent file — existing agents gain
conditional security analysis.

- Pros: no new agent file. Reuses existing roles.
- Cons: overloads TL and QA with dual responsibilities. Security review in the
  same agent context as architecture/QA risks blending concerns. TL focus is
  minimal architecture, not security depth. QA focus is acceptance criteria, not
  compliance profiles. Security expertise framing is diluted by the host role.
  Harder to maintain — security-specific prompt text mixed into general-purpose
  agent definitions.

### Option C: Command-only (no agent, just `/security-review`)

A `/security-review` command with no backing agent definition. Any agent or
the user's default agent can run it.

- Pros: simplest implementation. No new agent file.
- Cons: no consistent security reviewer persona. Review quality depends on
  which agent happens to run the command. No dedicated inputs/outputs contract.
  Inconsistent with the framework's agent-per-role model.

## Decision

**Option A is accepted.** A dedicated 7th agent role (`security.mdc`) with a
`/security-review` command and scratchpad flag control.

### Rationale

1. **Separation of concerns**: security review is a distinct expertise that
   should not be mixed with architecture design (TL) or acceptance testing (QA).
2. **Consistent pattern**: every other role has a dedicated agent file. Adding
   security as a 7th role follows the established convention.
3. **Zero overhead when disabled**: `SECURITY_REVIEW=0` (default) means the
   agent and command are never invoked. No impact on projects that don't need it.
4. **Focused context**: the security agent loads compliance profiles and
   security-specific review criteria without diluting other agents' prompts.
5. **Clean workflow integration**: `/auto` conditionally spawns the security
   agent at the right points (post-architecture, post-execute) only when enabled.

## Consequences

- Agent count increases from 6 to 7 (optional). Template and installer file
  classification lists need updating (framework files).
- `/auto` command gains conditional security review steps between existing
  phases. Complexity is minimal — one `if SECURITY_REVIEW=1` check at two
  points.
- Compliance profiles are prompt-embedded checklists in the agent definition,
  not external data. This keeps the framework self-contained.
- Critical security findings create DEC-xxxx records and block progression,
  integrating with the existing decision gate pattern.
- Template parity requires: `security.mdc`, `security-review.md` (command),
  `security-review.md` (placeholder report), scratchpad flag additions.
