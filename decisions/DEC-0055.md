# DEC-0055: Scratchpad example-only install policy with materialized baseline

- Date: 2026-03-23
- Status: Accepted
- Story: `US-0073`
- Research refs: `R-0050`
- Related: `DEC-0039` (example refresh + ownership), `US-0018` / `US-0057`
  (upgrade + scratchpad contracts), `R-0049` (merged scratchpad reload for `/auto`
  phase plans — loaders must recompute from merged bytes consistently)

## Context

Installers today may ship both `.cursor/scratchpad.md` (framework baseline) and
`.cursor/scratchpad.local.example.md` (framework-owned defaults). Operators want
a **simpler default delivery**: ship the **example** as the primary framework
artifact and avoid redundant committed baseline files, **without** breaking
deterministic automation (`/auto` and phase commands), upgrade safety, or
cross-surface parity.

`R-0050` defined **Model A** (committed baseline + example) vs **Model B**
(example-only with explicit materialization). This decision selects **Model B**
as the canonical **default install** policy for new/clean targets.

## Decision

### 1. Canonical delivery model (Model B — example-only)

1. **Framework ships** `.cursor/scratchpad.local.example.md` (and docs) as the
   authoritative **default key catalog** for discoverable automation flags.
2. **Effective baseline** for merge (see §2) is **not** assumed to exist as a
   third committed template file on disk after install unless **materialized**
   by an explicit, auditable step (install, first-run generator, or documented
   CLI action) that writes stable baseline bytes equivalent to the prior
   committed `scratchpad.md` shape.
3. **Never** infer missing required keys silently: absent or invalid values
   after merge **fail closed** with diagnostics naming the layers consulted
   (`local`, `baseline|materialized`, `example`) and remediation (`US-0073`
   `AC-2`, `AC-4`).

### 2. Canonical merged precedence (single invariant)

After each participating file is loaded as a key/value set, resolve **in this
order** (later steps only fill gaps):

1. **`.cursor/scratchpad.local.md`** — user-owned; highest precedence; **must
   never** be deleted or overwritten by install/upgrade (`DEC-0039`, `US-0018`).
2. **Materialized or legacy baseline** — repo `.cursor/scratchpad.md` when
   present (upgrade/legacy), **or** the materialized baseline produced under
   Model B (must be **stable and auditable**: same bytes as the historical
   committed baseline or a documented generated equivalent).
3. **`.cursor/scratchpad.local.example.md`** — framework-owned; supplies
   defaults only for keys not set above; refreshed on upgrade per `DEC-0039`.

Exact parser/merge mechanics (comments, ordering, invalid lines) are
implementation details; **this precedence order** is the architecture invariant.

### 3. Upgrade and legacy migration

1. Repos that **already** have committed `.cursor/scratchpad.md` **retain** it;
   upgrade continues to refresh **only** framework-owned example content and
   preserves user local (`DEC-0039`).
2. **Ambiguity is a defect**: if migration from “dual committed files” to
   example-only is invoked, the runbook/installer must document whether an
   existing committed baseline is preserved, replaced by materialized template, or
   left untouched — with deterministic behavior per path.

### 4. Parity surfaces

`installer.ps1`, `installer.sh`, `installer.py`, CLI entrypoints, and `template/`
trees must implement the **same** Model B policy and merge semantics (`US-0073`
`AC-6`, `AC-8`).

### 5. Minimum failure diagnostics (reason codes)

Implementation and tests should align with backlog `AC-9` / `AC-10`; minimum
operator-facing families include (exact strings may be refined in execute):

- Missing materialized baseline when required by the active path.
- Missing required key after full merge (layer attribution).
- Invalid value / parse failure at a named layer.

## Consequences

- Clean installs default to **example + materialization** rather than two
  parallel committed scratchpad artifacts.
- Command loaders **must** treat “no `scratchpad.md` until materialized” as a
  valid state and either materialize deterministically or fail closed — never
  silent permissive defaults.
- Sprint work implements materialization, migration messaging, tests, and docs
  (`README`, runbook) per `US-0073` acceptance criteria.

## Options considered

1. **Model A — committed baseline + example (status quo shape)** — Rejected as
   the **default** for `US-0073` scope because it preserves redundant delivery;
   remains a valid **legacy** state after upgrade.
2. **Model B — example-only + materialized baseline (chosen)** — Meets
   simplification goal while preserving deterministic merge and `DEC-0039`
   ownership boundaries.
