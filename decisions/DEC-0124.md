## Decision

### 1. Plugin entry point = `template/.opencode/plugins/orchestrator.ts` via v2 `Plugin.define` + auto-discovery (DQ1 LOCKED — AC-1, AC-2)

The orchestrator plugin ships as a single TypeScript file at `template/.opencode/plugins/orchestrator.ts` with the canonical v2 module shape:

```ts
import { Plugin } from "@opencode-ai/plugin";

export default Plugin.define({
  id: "its-magic.orchestrator",
  setup(ctx) {
    // ctx.tool.hook("execute.before", ...) — write-guard (DQ8)
    // ctx.session.create({ parentID, agent, prompt }) — spawn (DQ2)
    // subprocess scripts/auto_outer_driver.py — stop-matrix (DQ6)
  },
});
```

- **Auto-discovery**: OpenCode automatically scans `.opencode/plugins/` in every discovered OpenCode config directory and loads direct `.ts`/`.js` children. No `plugins[]` entry in `opencode.json` is required for auto-discovery. A repo-root or `.opencode/opencode.json` `plugins[]` entry is **optional** and only needed if the operator wants to pass `options` to the plugin or pin a non-default path. US-0121 ships no `opencode.json` in template (Q6 US-0121 lock); US-0124 inherits this — the plugin file alone is sufficient.
- **Filename choice**: `orchestrator.ts` is preferred over `index.ts` because (i) the v2 docs show single-purpose plugins named by purpose (`reviewer.ts`, `guards.ts`), (ii) `index.ts` is the child-directory-package convention — using it for a single file would imply a package boundary that does not exist, (iii) the `id` field (not the filename) is the disable/enable selector, so a descriptive filename aids operator readability while the `id` enables `--pure` / `-its-magic.orchestrator` disable directives.
- **Plugin id**: `its-magic.orchestrator` (namespaced; stable across US-0124..US-0126; operators disable via `--pure` or `-its-magic.orchestrator` on `opencode run`).

**Rejected alternatives**: (a) `index.ts` — rejected as the child-directory-package convention; (b) `opencode.json` `plugins[]` entry as required — rejected as unnecessary (auto-discovery suffices) and would force US-0121 to ship an `opencode.json` (Q6 US-0121 lock preserved); (c) v1 `@opencode-ai/plugin` default-export shape — rejected as the v1 path; v2 is the documented forward path (R-0109 Q1 LOCKED for /architecture as v2).

### 2. Spawn API = v2 `ctx.session.create({ parentID, agent, prompt })` + `ctx.session.wait(sessionID)` (DQ2 LOCKED — AC-1, AC-3, AC-4)

The v2 plugin context exposes `ctx.session` with `create`, `get`, `prompt`, `command`, `rename`, `synthetic`, `interrupt`, `wait`, and `hook`. There is **no** `ctx.task` or `ctx.agent.spawn` handle in v2 — `ctx.agent` exposes only `list`, `get`, `transform`, `reload` (no spawn). `ctx.session.create` is the documented spawn primitive.

The orchestrator plugin's spawn sequence:

1. Resolve `phase_id → role` via US-0069 / DEC-0051 matrix (compose, not amend).
2. Call `ctx.session.create({ parentID: <orchestrator-session-id>, agent: <role-agent-name>, prompt: <phase-prompt> })`.
3. Assert the returned `sessionID !== parentID` (DQ5 detection matrix — hard post-condition).
4. `ctx.session.wait(sessionID)` and read the final result.
5. Persist isolation evidence (AC-3): `parentID`, `sessionID`, `role`, `phase_id`, `timestamp`, `fresh_context_marker`.

The `parentID` field is the isolation anchor — passing the orchestrator's own `sessionID` as `parentID` creates an isolated child session; omitting `parentID` creates a sibling session (also isolated). The plugin MUST pass `parentID: <orchestrator-session-id>` to create an isolated child session for the spawned role agent.

If `ctx.session.create` is unavailable at runtime (host older than docs, or `--pure` / `-its-magic.orchestrator` / `OPENCODE_DISABLE_DEFAULT_PLUGINS` disabled the plugin), fail closed with `OPENCODE_PLUGIN_SPAWN_UNSUPPORTED` (DQ4). Do NOT degrade to same-session roleplay (R-0001).

### 4. Reason-code namespace — four new `OPENCODE_*` + three reused codes + stub runbook table (DQ4 LOCKED — AC-8; critic NB `ik_us0124_dq6_driver_fail_code_conflation` closed)

Introduce **four** namespaced `OPENCODE_*` codes for OpenCode-host-specific failure modes that have no Cursor-side equivalent:

- `OPENCODE_PLUGIN_SPAWN_UNSUPPORTED` — v2 `ctx.session.create` is unavailable at runtime (host older than docs, or plugin disabled via `--pure` / `-its-magic.orchestrator` / `OPENCODE_DISABLE_DEFAULT_PLUGINS`). Plugin cannot spawn; fail closed; do NOT degrade to same-session roleplay.
- `OPENCODE_SUBTASK_IGNORED` — `ctx.session.create` returned null/threw/identical-id (DQ5 matrix); spawn was a no-op; fail closed; stop `/auto`.
- `OPENCODE_HEADLESS_UNSUPPORTED` — US-0092 `--invoke-cmd` on OpenCode cannot resolve the non-interactive session CLI `opencode run` (DQ7 fail-closed path). Reserved for the **missing `opencode run` CLI surface only** — do NOT emit this code for Python driver subprocess failure (critic NB `ik_us0124_dq6_driver_fail_code_conflation` closed).
- `OPENCODE_DRIVER_INVOKE_FAILED` — `scripts/auto_outer_driver.py` subprocess invocation failed (non-zero exit, malformed JSON response, or timeout) when the plugin delegates a stop-matrix decision to the Python SOT (DQ6). Distinct from `OPENCODE_HEADLESS_UNSUPPORTED` (which is reserved for the missing `opencode run` CLI surface). Emitted by the plugin's subprocess-error handler; fail closed; stop `/auto`.

Reuse existing codes (do NOT introduce OpenCode-prefixed duplicates) for the cross-host concepts:

- `AUTO_ORCHESTRATOR_PHASE_EXECUTION` — orchestrator (or any role) performing another role's artifact writes (AC-1 spawn-only deny). Same semantics on both hosts.
- `PHASE_ROLE_MISMATCH` — wrong-role spawn per US-0069 / DEC-0051 matrix. Same semantics on both hosts.
- `NATIVE_CHAIN_UNAVAILABLE` — headless fallback when native in-session chain unavailable (compose with `OPENCODE_HEADLESS_UNSUPPORTED`: the latter is the OpenCode-specific trigger; the former is the cross-host stop-reason family).

**Precedence table location**: US-0124 ships a **stub reason-code table** in the US-0124 runbook section of `docs/engineering/runbook.md` (h2 anchor `## OpenCode orchestrator plugin reason codes (US-0124)`). The stub lists the four new `OPENCODE_*` codes + the three reused codes with one-line semantics + the fail-closed action. **US-0126 owns the full reason-code table text** (cross-host consolidated table); US-0124 ships the stub only — no duplication of remediation text. The stub cross-links to US-0126 for the full table.

### 5. Three-case subtask-ignored detection matrix + throw-discrimination rule (DQ5 LOCKED — AC-8)

The v2 docs do not explicitly document the failure modes of `ctx.session.create`. Three observable failure modes are possible at runtime when the host cannot or will not create an isolated child session:

- (i) **Returns `null` / `undefined`**: `ctx.session.create(...)` resolves to a null/undefined session handle. The plugin treats this as "spawn was ignored" — no child session was created.
- (ii) **Throws**: `ctx.session.create(...)` rejects with an error. The plugin catches and discriminates (see throw-discrimination rule below).
- (iii) **Returns a session id identical to the parent**: `ctx.session.create({ parentID: X, ... })` resolves to `{ sessionID: X }` — the host returned the same session, not a child. This is the most insidious failure mode because it appears to succeed. The plugin MUST compare `sessionID !== parentID` and fail closed if they match.

**Throw-discrimination rule** (LOCKED):

- If the thrown error indicates the spawn primitive itself is missing (e.g. `ctx.session.create is not a function`, `no such method`, `plugin API unsupported`) → emit `OPENCODE_PLUGIN_SPAWN_UNSUPPORTED` (the host cannot spawn at all).
- Otherwise (null return, identical-id return, or a generic throw that still indicates the spawn was ignored — e.g. `subagent not found`, `permission denied`, `host does not support spawn`) → emit `OPENCODE_SUBTASK_IGNORED` (the host could spawn but did not create an isolated child).

The plugin's `ctx.session.create` call site MUST include the `sessionID !== parentID` assertion as a hard post-condition. In all three cases, the plugin MUST NOT continue `/auto` (no next-phase spawn, no artifact write). The detection matrix is the contract: any one of the three signals triggers fail-closed. `test_us0124_subtask_ignored_fail_closed` runs three sub-tests (`_null_return`, `_throw`, `_identical_id`) covering the matrix.

### 6. Subprocess `scripts/auto_outer_driver.py` is the single TS↔Python integration; forbidden TS reimpl (DQ6 LOCKED — AC-6; critic NBs `ik_us0124_dq6_argv_extension_gap` + `ik_us0124_dq6_driver_fail_code_conflation` closed)

US-0092 / DEC-0078 owns the outer driver + stop reasons (decision_gate, loop_max, blocked, pause) + `--invoke-cmd`. The Python `scripts/auto_outer_driver.py` is the SOT for the state machine. The plugin (TypeScript) integrates with the stop-matrix (Python) via **subprocess** — the single integration. **Forbidden**: reimplementing the US-0092 state machine in TypeScript (two SOTs would drift; the Python validators (US-0125) and the TS plugin would diverge on edge cases).

**Exact argv contract** (locked — T-004 is an **additive** CLI extension; critic NB `ik_us0124_dq6_argv_extension_gap` closed):

```
python scripts/auto_outer_driver.py --phase <phase_id> --role <role> --story <story_id> --sprint <sprint_id> --orchestrator-run-id <run_id> --stop-reason <reason>
```

- The driver returns a JSON object on stdout: `{ "action": "spawn_next" | "hard_stop" | "ledger_write" | "pause_boundary", "next_phase": "<phase_id>", "stop_reason": "<reason>", ... }`.
- The plugin parses the JSON and dispatches: `spawn_next` → `ctx.session.create` for the next phase; `hard_stop` → emit stop reason + halt; `ledger_write` → write to ledger + continue; `pause_boundary` → emit pause + halt.
- The plugin does NOT own stop-reason logic; it only parses + dispatches. All state-machine transitions live in `scripts/auto_outer_driver.py` (Python SOT).
- **Additive extension**: when the new flags (`--phase/--role/--story/--sprint/--orchestrator-run-id/--stop-reason`) are **absent**, the existing `auto_outer_driver.py` behavior is byte-identical (no regression to US-0092 / DEC-0078). The new flags are parsed only when present and produce the JSON response; the legacy CLI surface is untouched.

**Subprocess error-handling contract** (critic NB `ik_us0124_dq6_driver_fail_code_conflation` closed):

- Non-zero exit code from `auto_outer_driver.py` → emit `OPENCODE_DRIVER_INVOKE_FAILED` (NOT `OPENCODE_HEADLESS_UNSUPPORTED`); fail closed; stop `/auto`.
- Malformed JSON response (parse error) → emit `OPENCODE_DRIVER_INVOKE_FAILED`; fail closed; stop `/auto`.
- Subprocess timeout → emit `OPENCODE_DRIVER_INVOKE_FAILED`; fail closed; stop `/auto`.
- `opencode run` CLI missing on PATH (DQ7 headless path, separate from DQ6) → emit `OPENCODE_HEADLESS_UNSUPPORTED`; fail closed; stop `/auto`.

`OPENCODE_HEADLESS_UNSUPPORTED` is reserved exclusively for the missing `opencode run` CLI surface (DQ7). `OPENCODE_DRIVER_INVOKE_FAILED` is reserved exclusively for the Python driver subprocess failure (DQ6). The two codes are distinct and never overlap.

### 7. Headless CLI = `opencode run --agent auto --format json --auto` + fail-closed `OPENCODE_HEADLESS_UNSUPPORTED` (DQ7 LOCKED — AC-7)

`https://opencode.ai/docs/cli/` documents **`opencode run "<prompt>"`** as the public, stable, non-interactive CLI surface. Flags confirmed: `--agent <agent-name>`, `--model provider/model-id`, `--command <command>`, `--format default|json`, `--attach <url>`, `--auto`, `--continue` / `--session <id>` / `--fork`, `--dir <path>`, `--title <title>`.

US-0092 `--invoke-cmd` on OpenCode maps to:

- **Primary**: `opencode run --agent auto --format json --auto "<phase-prompt>"` — non-interactive, structured JSON output, auto-approve permissions. The outer driver (`scripts/auto_outer_driver.py`) parses the JSON events for the phase result + stop reason.
- **Optional optimization**: `opencode serve` + `opencode run --attach http://localhost:4096 --agent auto --format json --auto "<phase-prompt>"` — avoids MCP cold boot across multiple phase invocations within one `/auto` run. The outer driver may start a `serve` instance once per `/auto` run and attach subsequent `run` calls.
- **Fail-closed path**: if `opencode run` is not on PATH (e.g. OpenCode not installed, or `--pure` mode disables the plugin), the outer driver emits `OPENCODE_HEADLESS_UNSUPPORTED` and stops. Do NOT silently degrade to a TUI launch or same-session roleplay. `test_us0124_invoke_cmd_hook` asserts the wiring (argv construction + JSON parsing) OR the fail-closed path — not a live OpenCode probe.

### 8. Agent vs plugin ownership boundary — independent surfaces, defense in depth, no permission-array duplication (DQ8 LOCKED — AC-1, AC-9)

US-0122 / DEC-0122 ships `template/.opencode/agents/auto.md` — the orchestrator **agent** (prompt layer): `mode: primary`, `edit: deny`, `bash: deny`, `task` allow-list to seven role agents. The agent tells the model "you are the auto orchestrator; spawn Task subagents only" and constrains permissions. US-0124 ships the orchestrator **plugin** (enforcement layer): `ctx.tool.hook("execute.before", ...)` intercepts tool calls, `ctx.session.create(...)` spawns isolated child sessions, `ctx.session.hook("context", ...)` can strip tools before dispatch, and the plugin calls `scripts/auto_outer_driver.py` (DQ6) for stop-matrix decisions. The two surfaces are **independent**:

- **Agent** owns: *who the model is* (system prompt, role identity) + *what tools the model may request* (permission allow-list: `edit: deny`, `bash: deny`, `task` 7-role allow-list).
- **Plugin** owns: *what the host does* (spawn isolated child sessions, write-guard enforcement via `ctx.tool.hook`, stop-matrix dispatch via subprocess, isolation evidence persistence).

The agent's permission array is the **first** enforcement layer (the model never sees denied tools). The plugin's `ctx.tool.hook("execute.before")` is the **second** enforcement layer (the host refuses any tool call that slipped past the agent's permission array, e.g. a prompt-ignoring model attempting an `edit`). Defense in depth — the two layers do not duplicate; they complement.

The plugin MUST **NOT** copy the agent's permission array into its own source. The plugin's `ctx.tool.hook("execute.before")` enforces a **different** rule: "the orchestrator (or any role) must not perform another role's artifact writes" — i.e. `AUTO_ORCHESTRATOR_PHASE_EXECUTION`. The agent's permission array enforces "the orchestrator may not edit/bash" — a different rule. The two rules compose: the agent blocks the tool request at the model layer; the plugin blocks the artifact write at the host layer. `test_us0124_agent_plugin_compose` asserts:

- (i) both files exist: `template/.opencode/agents/auto.md` (US-0122) + `template/.opencode/plugins/orchestrator.ts` (US-0124).
- (ii) the plugin source does NOT contain the agent's `task` allow-list (grep for the 7 role names in the plugin source — must be zero matches; the plugin resolves roles via US-0069 matrix, not via a hardcoded list).
- (iii) the plugin source does NOT contain the agent's `edit`/`bash` permission literals (grep for `edit:` / `bash:` in the plugin source — must be zero matches; the plugin's write-guard is path-based via `ctx.tool.hook`, not permission-array-based).
- (iv) the plugin's `ctx.tool.hook("execute.before")` callback exists and calls into the stop-matrix subprocess (DQ6) for `AUTO_ORCHESTRATOR_PHASE_EXECUTION` detection.
