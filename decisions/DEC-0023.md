# DEC-0023: Explicit Bulk Planning Mode for `/sprint-plan`

## Status

Accepted

## Context

Users need higher planning throughput for large OPEN backlogs without manually
running `/sprint-plan` repeatedly for each story. At the same time, planning
must remain bounded, deterministic, and safe under existing sprint sizing
constraints.

Current `/sprint-plan` behavior is non-bulk by default and does not define an
explicit command-level contract for multi-story planning in one run.

## Decision Drivers

- Preserve current default-safe non-bulk planning behavior.
- Provide explicit operator intent for high-impact bulk planning.
- Keep deterministic selection/grouping and reproducible outputs.
- Enforce bounded controls to prevent runaway planning runs.
- Preserve sizing constraints and artifact completeness per generated sprint.

## Options Considered

### Option A: Keep current non-bulk planning only

- **Pros**: no new contract complexity.
- **Cons**: low throughput for large backlogs; high manual repetition.

### Option B: Implicit bulk planning based on backlog size

- **Pros**: minimal user input.
- **Cons**: ambiguous intent, surprising behavior, and weaker safety/auditability.

### Option C: Explicit bulk planning trigger with bounded deterministic policy (chosen)

- **Pros**:
  - clear intent boundary between normal and bulk behavior
  - deterministic and auditable selection/grouping
  - bounded execution with explicit stop reasons
- **Cons**:
  - adds policy controls and regression/test complexity

## Decision

Adopt Option C:

1. Add explicit bulk trigger semantics for `/sprint-plan`.
2. Keep non-bulk planning as default when trigger is absent.
3. Use deterministic story selection (priority, then backlog order).
4. Enforce bounded limits (max stories and/or max generated sprints per run).
5. Preserve sprint sizing controls (`SPRINT_MAX_TASKS`, `SPRINT_AUTO_SPLIT`) and
   per-sprint artifact completeness.

## Consequences

### Positive

- Higher planning throughput for large backlogs.
- Predictable behavior with stable ordering and explicit bounds.
- Better auditability via deterministic stop reasons and planning breadcrumbs.

### Negative

- More orchestration policy surface in `/sprint-plan`.
- Additional QA matrix needed for boundary and grouping/splitting behavior.

### Neutral / Follow-up

- This decision is planning-only; execution orchestration is addressed separately
  in `DEC-0024` (`US-0047`).
