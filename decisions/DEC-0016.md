# DEC-0016: Remote Config Contract and Mode-Aware Validation

## Status: Accepted

## Context

US-0036 requires an official and safe remote execution configuration approach.
The repo already exposes `REMOTE_EXECUTION` and `REMOTE_CONFIG` flags, but
without a canonical config artifact and explicit validation contract, behavior
is ambiguous and error-prone.

Architecture must remain process-level:
- in scope: config contract, validation behavior, error model, security guidance
- out of scope: implementing remote transport/orchestrator backends

The default experience must remain non-blocking when remote execution is off.

## Options

### Option A: No config file, ad-hoc remote behavior

Use implicit assumptions and per-command ad-hoc handling, without a canonical
`remote.json` contract.

- Pros: minimal upfront documentation work.
- Cons: inconsistent behavior, hard-to-debug failures, weak safety posture,
  poor parity across active/template installs.

### Option B: Optional loose config with best-effort parsing

Provide an optional config file with permissive parsing and warning-only checks.

- Pros: lower immediate friction for teams experimenting with remote mode.
- Cons: late failures, ambiguous semantics, hidden misconfiguration risk, weak
  quality gate behavior.

### Option C: Canonical JSON contract + fail-fast validation when enabled

Define `.cursor/remote.json` as the contract file (with template parity), and
enforce strict validation only when `REMOTE_EXECUTION=1`.

- Pros: deterministic setup, early actionable failure, clear security policy,
  preserves zero-overhead default-off behavior.
- Cons: requires explicit schema documentation and maintenance discipline.

## Decision

**Option C is accepted.**

Adopt a canonical remote config contract:
- Active file: `.cursor/remote.json`
- Template file: `template/.cursor/remote.json`

Adopt mode-aware validation:
- `REMOTE_EXECUTION=1` -> fail-fast validation for missing/malformed/invalid or
  insecure config.
- `REMOTE_EXECUTION=0` -> skip remote config checks entirely (zero overhead).

Adopt actionable error reporting:
- every error includes failing path, expected rule, actual value/type, and fix.

Adopt security constraints:
- no committed secrets in `remote.json`
- env-var references only for sensitive values.

## Consequences

- Remote-enabled workflows become predictable and safer due to strict contract
  and immediate feedback on invalid configuration.
- Docs/runbook must stay aligned with contract details and error semantics.
- Teams get no behavior change in default mode (`REMOTE_EXECUTION=0`).
- Validation guidance can be decomposed into sprint tasks without claiming
  runtime orchestrator implementation.

## Risks

- **Contract drift risk:** active/template copies and docs can diverge.
  - Mitigation: parity checks and same-change-set updates for contract changes.
- **Over-strict validation risk:** could block legitimate future target types.
  - Mitigation: extend allowed values via explicit decision records.
- **False secret detection risk:** heuristic checks may over-flag placeholders.
  - Mitigation: document accepted placeholder patterns and remediation examples.
