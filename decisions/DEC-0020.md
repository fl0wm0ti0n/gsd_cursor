# DEC-0020: Per-Sprint Immutable Release Notes and Canonical Release Queue

## Status

Accepted

## Context

US-0040 requires release-history preservation and deterministic tracking of
unreleased versus released sprints. Current behavior uses a single mutable
`handoffs/release_notes.md`, which is vulnerable to overwrite and does not
provide a canonical per-sprint release state model.

The architecture must:
- prevent cross-sprint overwrite,
- define deterministic transitions for release readiness/finalization,
- preserve backward compatibility for workflows reading legacy release notes,
- provide non-destructive migration/backfill,
- fail safely when sprint resolution or queue/notes metadata is inconsistent.

## Decision Drivers

- Preserve release history across sprints without destructive mutation.
- Make pending unreleased sprints visible and queryable in one canonical place.
- Keep release transitions deterministic and auditable.
- Preserve compatibility for existing consumers of `handoffs/release_notes.md`.
- Keep defaults safe (fail closed, non-destructive) under ambiguity or mismatch.
- Keep scope process/workflow-level without deployment-system redesign.

## Options Considered

### Option A: Keep single mutable `handoffs/release_notes.md`

- **Description**: Continue writing all releases into one mutable file.
- **Pros**: Lowest immediate change; no migration artifacts needed.
- **Cons**:
  - High overwrite risk across sprints.
  - No canonical queue for unreleased/released visibility.
  - Weak deterministic state-transition model.
  - Fails core US-0040 non-overwrite intent.

### Option B: Keep single file and append historical sections

- **Description**: Keep one file but append sprint sections chronologically.
- **Pros**: Preserves one-file discoverability; some history retention.
- **Cons**:
  - Queue state remains implicit and hard to validate.
  - Increased formatting/parsing inconsistency risk over time.
  - Backfill and partial-failure recovery remain ambiguous.
  - Still centralizes all writes in one high-conflict artifact.

### Option C: Per-sprint immutable notes plus canonical queue index (chosen)

- **Description**:
  - Release notes live per sprint at
    `handoffs/releases/Sxxxx-release-notes.md`.
  - Canonical queue lives at `handoffs/release_queue.md`.
  - Legacy `handoffs/release_notes.md` remains as backward-compatible latest
    pointer/summary.
- **Pros**:
  - Strong non-overwrite guarantee by sprint-scoped artifacts.
  - Deterministic status lifecycle per sprint.
  - Clear migration/backfill contract and failure-safe behavior.
  - Better release observability for pending unreleased work.
- **Cons**:
  - Introduces queue artifact and compatibility-pointer maintenance.
  - Requires migration handling for legacy single-file notes.

## Decision

Adopt Option C.

Canonical model:
1. Write sprint release notes to
   `handoffs/releases/Sxxxx-release-notes.md` only.
2. Track sprint release status in `handoffs/release_queue.md`.
3. Keep `handoffs/release_notes.md` for backward-compatible latest-pointer
   behavior (not canonical history).

Deterministic transitions:
- `planned -> ready -> unreleased -> released`
- `blocked` for deterministic failure conditions.

Transition rules:
- Only the target sprint row may change during a `/release` run.
- Entering release flow for a resolved sprint creates/updates `unreleased`.
- Successful finalization transitions only that sprint to `released`.
- On unresolved sprint identity or inconsistent metadata, fail closed and do not
  overwrite/alter unrelated sprint note artifacts.

## Rationale

Per-sprint artifacts are the simplest robust way to eliminate overwrite while
preserving history integrity. A separate queue index provides deterministic
state tracking and visibility for unreleased work, which single-file strategies
cannot represent cleanly without fragile parsing conventions.

Retaining `handoffs/release_notes.md` as a latest-pointer bridge preserves
backward compatibility and allows staged migration without breaking existing
read paths.

## Consequences

### Positive

- Historical release notes become immutable by sprint.
- Unreleased/released status becomes explicit and auditable.
- Failure handling is safer: ambiguous state cannot silently corrupt history.
- Release readiness views can surface pending unreleased sprint entries.

### Negative

- Additional artifact maintenance (`release_queue.md`) is required.
- Release guidance and template references must be updated in lockstep.
- Legacy migration introduces one-time operational complexity.

### Neutral / Follow-up

- Queue formatting (table or structured sections) can be implementation-specific
  as long as required fields and transition semantics remain deterministic.
- Tooling can later automate queue integrity checks, but initial delivery stays
  workflow-guidance focused.

## Migration Plan

One-time non-destructive backfill from legacy `handoffs/release_notes.md`:

1. Attempt sprint resolution using legacy note content and current state context.
2. If resolvable:
   - create `handoffs/releases/Sxxxx-release-notes.md` from legacy content,
   - keep legacy file and append/update pointer summary.
3. If unresolved:
   - preserve legacy file unchanged,
   - record queue entry with `blocked` and reason
     `LEGACY_NOTES_SPRINT_UNRESOLVED`,
   - provide manual migration guidance.
4. Migration must be idempotent (do not recreate/overwrite existing sprint file
   for same sprint unless explicitly requested).

## Failure-Safe Policy

When queue and notes metadata is inconsistent:
- fail release finalization closed,
- preserve existing notes artifacts,
- emit deterministic reason codes in queue/state artifacts:
  - `RELEASE_SPRINT_UNRESOLVED`
  - `QUEUE_ENTRY_MISSING`
  - `NOTES_REF_MISSING`
  - `STATUS_TRANSITION_INVALID`
- provide remediation instructions and require rerun after correction.

No destructive reconciliation is allowed by default.
