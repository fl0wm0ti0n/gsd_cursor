# DEC-0046: OS-aware runbook command bootstrap contract

- Date: 2026-03-15
- Status: Accepted
- Story: `US-0063`

## Context

New repositories could be blocked early because `docs/engineering/runbook.md`
did not contain a usable `TEST_COMMAND`. Operators also reported OS mismatch
issues (for example `sh` defaults in Windows contexts), while quality-gate
policy still requires a real baseline test command.

## Decision

Adopt deterministic installer-time runbook bootstrap for command keys with
explicit precedence and fail-fast diagnostics:

1. Precedence:
   - `user override > detected defaults > fail-fast diagnostics`
2. Required baseline:
   - `TEST_COMMAND` must resolve to a valid, detectable command.
3. Optional defaults:
   - `LINT_COMMAND` / `TYPECHECK_COMMAND` are populated only when confidently
     detectable from stack signals.
4. Detection surface:
   - `package.json` scripts (`test`, `lint`, `typecheck`)
   - `pyproject.toml` / `requirements.txt` / `setup.py`
   - `go.mod`
   - platform test scripts (`tests/run-tests.ps1`, `tests/run-tests.sh`)
5. Deterministic diagnostics:
   - unresolved baseline: `[RUNBOOK_BOOTSTRAP_ERROR] TEST_COMMAND_UNRESOLVED`
   - invalid candidate: `[RUNBOOK_BOOTSTRAP_ERROR] TEST_COMMAND_INVALID:<reason>`
6. Non-destructive behavior:
   - non-empty user runbook command values are preserved on reruns/upgrades.

## Consequences

- First-run onboarding is less likely to block when stack markers exist.
- Quality gate semantics remain strict (`TEST_COMMAND` is still mandatory).
- Install/upgrade scripts now include command validation and explicit remediation
  guidance.
