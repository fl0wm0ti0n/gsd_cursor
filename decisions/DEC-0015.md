# DEC-0015: Component Scope Guard Model

## Status: Accepted

## Context

US-0035 requires teams to execute work on selected components without
destabilizing non-target components in multi-component repositories. The model
must support explicit scope declaration, guardrails during execution, QA
protection checks, and decision gates for unapproved out-of-scope impact.

The feature must be optional and zero-overhead when disabled.

## Options

### Option A: Advisory-only scope notes

Allow informal scope notes in sprint tasks without hard guard conditions.

- Pros: minimal process overhead.
- Cons: weak protection; out-of-scope impact can slip through without escalation
  or evidence requirements.

### Option B: Declarative scope artifact + QA guard checks + decision gate

Define scope in a canonical artifact, require task-level component tags, enforce
scope-first execution guidance, and trigger gate on unapproved out-of-scope
impact.

- Pros: concrete and testable process controls; aligns with existing
  decision-gate pattern; keeps runtime unchanged.
- Cons: extra artifact/checklist updates when mode is enabled.

### Option C: Hard technical sandboxing of file edits by component

Implement automated tooling to block edits outside component directories.

- Pros: strongest technical enforcement.
- Cons: outside workflow scope; brittle in mixed/shared interface files; higher
  implementation complexity.

## Decision

**Option B is accepted.** Adopt a declarative component-scope model with QA
protection checks and decision-gate escalation.

Canonical artifacts:
- `docs/engineering/component-scope.md`
- `docs/engineering/component-scope-report.md`

Control flags:
- `COMPONENT_SCOPE_MODE=0` (default)
- `TARGET_COMPONENTS=` (optional default targets)

Gate trigger:
- Scope mode on + detected out-of-scope impact + not pre-approved in scope
  artifact/decisions/handoffs.

## Consequences

- Teams can safely focus changes by component with explicit non-target
  protection evidence.
- QA has a deterministic checklist for unaffected-component validation.
- Escalation becomes explicit instead of accidental when scope expands.
- Default workflow remains unchanged when `COMPONENT_SCOPE_MODE=0`.
