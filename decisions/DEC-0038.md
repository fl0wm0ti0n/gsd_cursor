# DEC-0038: Strict Runtime Attestation Contract for `/auto` Phase Boundaries

- Date: 2026-03-14
- Status: Accepted
- Related story: US-0056
- Research refs: R-0034

## Context

US-0048 / DEC-0029 enforce artifact-level isolation evidence at phase boundaries,
but user feedback shows this is not sufficient as strict runtime proof of fresh
per-phase subagent execution. `/auto` needs a stronger, auditable runtime
attestation contract and deterministic fail-closed behavior.

## Proposed decision

1. Require a strict runtime attestation envelope for each completed phase run:
   - `orchestrator_run_id`
   - `runtime_proof_id`
   - `phase_id`
   - `role`
   - `proof_issued_at` (UTC/RFC3339)
   - `proof_ttl_seconds`
   - `proof_hash`
2. Enforce boundary validation in `/auto` before advancing to next phase.
3. Fail closed with deterministic reason codes on strict-proof violations:
   - `RUNTIME_PROOF_MISSING`
   - `RUNTIME_PROOF_INVALID`
   - `RUNTIME_PROOF_REUSED`
   - `RUNTIME_PROOF_STALE`
   - `RUNTIME_PROOF_AMBIGUOUS_LINK`
4. Extend pause/resume provenance and release/isolation gates to consume strict
   runtime-proof evidence in addition to existing artifact evidence.
5. Keep bounded legacy compatibility guidance without rewriting historical runs.

## Options considered

1. **Artifact-only evidence (status quo)**  
   Rejected for strict-proof scope; does not prove runtime uniqueness/freshness.
2. **Strict runtime attestation envelope + validator (recommended)**  
   Balances auditable strictness with bounded implementation complexity.
3. **External orchestrator identity provider**  
   Out of scope and too heavy for current workflow architecture.

## Consequences

- Improves confidence that `/auto` phase transitions reflect real fresh-context
  executions.
- Adds deterministic stop conditions that may block runs until remediation.
- Requires command/rule/docs/test updates with active/template parity.

## Decision outcome

- Approved option: **2** (strict runtime attestation envelope + boundary validator)
- Approval source: user
- Approval date: 2026-03-14

Implementation can proceed to sprint planning.
