# DEC-0024: Explicit Bulk Execute Mode with Team-Scoped Guardrails

## Status

Accepted

## Context

Users want autonomous bulk execution across planned sprints/stories so they do
not need to manually chain execution commands. This must remain safe in team
scenarios where multiple members can work in parallel and should not execute the
same tasks.

Existing `/auto` capabilities provide flag-driven backlog drain, but explicit
command-level semantics for team-scoped bulk execution and collision-safe task
ownership are not formally defined.

## Decision Drivers

- Preserve explicit operator control for high-impact bulk execution.
- Maintain strict fresh-context isolation per phase and execute/qa cycle.
- Prevent cross-member task collisions in team mode.
- Keep bounded controls and deterministic stop/skip behavior.
- Preserve decision gates and artifact-first auditability.

## Options Considered

### Option A: Keep relying on existing flag-driven `/auto` behavior only

- **Pros**: no new command contract.
- **Cons**: implicit intent, weaker team-scope clarity, higher misuse risk.

### Option B: Bulk execution without team-scope enforcement

- **Pros**: maximal throughput in single-user cases.
- **Cons**: unsafe for teams; duplicate work and conflicting writes likely.

### Option C: Explicit bulk execute mode with team-scope enforcement (chosen)

- **Pros**:
  - explicit activation and safer default behavior
  - deterministic bounded progression
  - member-scoped execution safety in team mode
- **Cons**:
  - added policy complexity and reason-code/test surface

## Decision

Adopt Option C:

1. Define explicit bulk execute activation semantics (command or mode argument).
2. Keep current non-bulk behavior as default when bulk mode is not enabled.
3. Require deterministic item selection and breadcrumb logging.
4. Enforce fresh-context isolation per phase and per execute↔QA cycle.
5. In team mode, restrict execution to current member scope
   (`TEAM_MEMBER` + `ACTIVE_TASK_IDS`) and deny writes for out-of-scope tasks.
6. Require bounded controls (max items, block/skip policy) and deterministic
   reason-code outcomes.

## Consequences

### Positive

- Enables high-autonomy execution with explicit safety boundaries.
- Reduces duplicate-work risk in concurrent team workflows.
- Improves inspectability through deterministic checkpoints and stop metadata.

### Negative

- More orchestration control paths to test and maintain.
- Requires strict handling of team-context correctness.

### Neutral / Follow-up

- This decision complements, but does not replace, existing `/auto` backlog-drain
  semantics (`DEC-0022`).
