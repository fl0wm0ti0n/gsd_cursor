# DEC-0051: Strict `/auto` phase→role mapping with preflight and fail-closed evidence alignment

- Date: 2026-03-20
- Status: Accepted
- Story: `US-0069`
- Research refs: `R-0048`
- Related: `DEC-0029` (isolation evidence), `DEC-0038` (strict runtime proof)

## Context

`/auto` orchestration can collapse high-privilege work (for example `execute`)
into an unintended role (commonly `tech-lead`) when role intent is documented
but not enforced before phase work starts. Post-hoc isolation markers alone do
not prevent silent substitution. `US-0069` requires admission-style **preflight**
resolution, single-valued expected roles at each boundary (including policy
alternates), checkpoint rejection on mismatch, and alignment between isolation
`role` and strict-proof `role` / `proof_hash` inputs.

## Decision

Adopt a deterministic **canonical phase→role contract** with **scratchpad policy
resolution** for allowed alternates, **mandatory preflight** before each phase
spawn, **fail-closed** behavior when capability is missing or evidence disagrees
with the contract, and **default deny** for non-`dev` execute contexts unless a
rare documented override path is satisfied.

### 1. Canonical phase→role matrix (fixed phases)

| phase_id | Allowed roles (logical) | Default when no alternate policy applies |
|----------|-------------------------|------------------------------------------|
| `intake` | `po` | `po` |
| `discovery` | `po` | `po` |
| `research` | `po`, `tech-lead` | `tech-lead` |
| `architecture` | `tech-lead` | `tech-lead` |
| `sprint-plan` | `tech-lead` | `tech-lead` |
| `plan-verify` | `qa`, `tech-lead` | `qa` |
| `execute` | `dev` (override path only for non-default) | `dev` |
| `qa` | `qa` | `qa` |
| `verify-work` | `qa` | `qa` |
| `release` | `release` | `release` |
| `closure` | `qe`, `curator` (via `AUTO_ROLE_CLOSURE` override) | `qe` |
| `refresh-context` | `curator`, `po` | `curator` |

### 2. Deterministic alternate-role policy (single-valued resolution)

For phases with alternates, `/auto` resolves **exactly one** expected role per
boundary using scratchpad keys (active + template parity on implementation):

- `AUTO_ROLE_RESEARCH`: `po` \| `tech-lead` (default `tech-lead` when unset or
  invalid).
- `AUTO_ROLE_PLAN_VERIFY`: `qa` \| `tech-lead` (default `qa` when unset or
  invalid).
- `AUTO_ROLE_CLOSURE`: `qe` \| `curator` (default `qe` when unset or invalid).
  `curator` must NOT write qa-owned surfaces (status flip + acceptance only).
- `AUTO_ROLE_REFRESH_CONTEXT`: `curator` \| `po` (default `curator` when unset or
  invalid).

Invalid values fail closed with deterministic diagnostics (no silent fallback to
an unrelated role).

### 3. Preflight capability gate (before spawn)

Before spawning phase work, `/auto` must:

1. Resolve `phase_id` → expected canonical `role` using the matrix + policy
   keys above.
2. Evaluate **role capability availability** for that boundary (deterministic
   check contract to be implemented in `/execute` story scope; architecture
   requires the gate to exist and to block when unavailable).
3. For `closure`, required capability is `role:qe` (default) or `role:curator`
   (override via `AUTO_ROLE_CLOSURE=curator`). `curator` must NOT write
   qa-owned surfaces. Fail-closed on unresolved capability: `PHASE_CASE_CAPABILITY_MISSING`.
4. On missing capability: stop with `PHASE_CASE_CAPABILITY_MISSING` including
   `phase_id`, expected role, observed capability result, and remediation
   (spawn correct role, fix policy, or satisfy override contract).

Post-hoc evidence alone is insufficient to satisfy the gate.

### 4. Checkpoint and strict-proof alignment

On phase completion, boundary validation must:

- Reject checkpoint completion when isolation evidence `role` ≠ expected
  resolved role for that `phase_id` (`PHASE_ROLE_MISMATCH`).
- Require strict runtime proof tuple (`DEC-0038`) where `role` equals the same
  resolved canonical role as isolation evidence.
- Ensure `proof_hash` is computed over the canonical JSON tuple (sorted keys) so
  linkage is auditable and consistent with `DEC-0038`.

### 5. Execute default deny and override

- **Default:** `execute` MUST require `dev`. Running `execute` as `tech-lead` or
  any other role is denied.
- **Override:** Non-`dev` execute is permitted only when **both** hold:
  1. Scratchpad sets `AUTO_EXECUTE_ROLE_OVERRIDE` to a single documented
     sentinel value (`allowed_non_dev_execute`) **and**
  2. The orchestration run records an explicit `execute_override_governance_ref`
     pointing to an approved exception record (for example a `DEC-xxxx` waiver
     or story-scoped governance entry in `docs/engineering/state.md`) that is
     present and parseable at the boundary.

If either is missing, treat as deny (fail closed). This satisfies AC-5 while
keeping overrides rare and auditable.

### 6. Resume and `start-from` parity

Resume resolution (`handoffs/resume_brief.md`, `start-from`, state fallback) must
not bypass preflight. Each continuation run re-executes role resolution and
capability checks from scratch.

### 7. Reason-code vocabulary (baseline)

Document and implement at minimum:

- `PHASE_ROLE_CAPABILITY_MISSING`
- `PHASE_ROLE_MISMATCH`

Additional codes may extend the family but must remain deterministic and
documented per AC-9.

## Alternatives considered

1. **Evidence-only enforcement (post-hoc validation)**  
   Rejected: allows incorrect-role execution to proceed until artifacts are
   written; fails discovery/research safety goals (`R-0048`).

2. **Implicit fallback to `tech-lead` when `dev` unavailable**  
   Rejected: violates AC-2, AC-5, and separation-of-duties intent.

3. **Hard-coded alternates without scratchpad policy**  
   Rejected: cannot satisfy AC-1 alternate phases deterministically in varied
   team setups.

## Consequences

- `/auto` gains a clear admission boundary for phase roles; more runs may stop
  until the correct subagent capability is available.
- Implementation must touch `/auto` command contract, scratchpad documentation,
  runbook/README, active/template parity, and regression tests (AC-7, AC-8).
- Release/readiness surfaces must be able to cite isolation + strict-proof
  evidence for lifecycle boundaries (AC-10), building on existing `DEC-0029` /
  `DEC-0038` fields.
