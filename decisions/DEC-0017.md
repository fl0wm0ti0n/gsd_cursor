# DEC-0017: Deterministic `/auto` Continuation Source Resolution and Control Model

- **Date**: 2026-02-25
- **Status**: Accepted
- **Story**: US-0037

## Context

The workflow already supports `/pause`, `/resume`, and `/auto`, but mid-process
continuation behavior is not explicit enough for deterministic automation.
Current semantics allow interpretation gaps:
- no explicit `/auto` `start-from` contract,
- unclear precedence when both `resume_brief` and `state.md` can imply a phase,
- inconsistent handling of stale/conflicting resume signals.

US-0037 requires one-command continuation from the right phase, preserving
existing gates and stop conditions, with inspectable breadcrumbs.

## Decision Drivers

- Deterministic and testable phase selection.
- Operator control for intentional override cases.
- Safe behavior: fail fast on ambiguity/conflict, never guess.
- Backward compatibility for manual and existing auto users.
- Minimal process-level scope (no runtime orchestration rewrite).

## Options Considered

### Option A: Keep current implicit behavior only

Description:
- Keep `/auto` and `/resume` behavior inference-heavy without explicit
  `start-from`.

Pros:
- Lowest implementation cost.
- No command signature changes.

Cons:
- Non-deterministic in ambiguous resume situations.
- Harder to debug and test.
- Does not satisfy US-0037 acceptance on explicit override and fail-fast policy.

### Option B: Resume-only continuation (no `/auto start-from`)

Description:
- Continue via `/resume` semantics only; `/auto` remains implicit.

Pros:
- Moderate complexity.
- Centralizes continuation on `resume_brief`.

Cons:
- No explicit operator override for recovery/control.
- Weak handling when resume brief is stale/missing.
- Splits continuation semantics across commands.

### Option C: Unified deterministic model with explicit override + fallback chain (chosen)

Description:
- `/auto` accepts `start-from=<phase>`.
- Without explicit override, resolve phase deterministically:
  1) explicit `/auto start-from`
  2) `handoffs/resume_brief.md`
  3) `docs/engineering/state.md` fallback
  4) fail-fast on ambiguity/conflict/unrecoverable state

Pros:
- Fully deterministic and acceptance-testable.
- Preserves manual defaults while enabling precise auto continuation.
- Strong safety posture with explicit fail-fast behavior.
- Adds inspectable breadcrumbs for auditability.

Cons:
- Requires command/rule documentation alignment work.
- Requires explicit resolver and error contracts.

## Decision

Choose **Option C**.

Adopt a unified deterministic continuation model for `/auto` with explicit
`start-from` support, strict precedence resolution, and fail-fast handling for
stale/conflicting/ambiguous inputs.

## Control Contract

### Canonical phase IDs

Accepted `start-from` values:
`intake`, `discovery`, `research`, `architecture`, `sprint-plan`,
`plan-verify`, `execute`, `qa`, `verify-work`, `release`, `refresh-context`.

Non-canonical or alias values are rejected with fail-fast error.

### Source precedence

Resolver order:
1. Explicit argument (`start-from=<phase>`)
2. Resume brief declared phase (`handoffs/resume_brief.md`)
3. Conservative `state.md` phase inference
4. Fail fast when unresolved/conflicting/ambiguous

### Conflict and staleness policy

- Explicit valid `start-from` always wins and is logged as override.
- If no explicit override and `resume_brief` conflicts with `state` inference:
  fail fast.
- If `resume_brief` exists but is stale/unparseable: fail fast (do not silently
  downgrade to state fallback).
- Use state fallback only when resume brief is absent.
- If state inference is ambiguous/unrecoverable: fail fast.

### Error messaging contract

Format:
`[AUTO_RESUME_ERROR] <code>: <summary>. Source=<source>. Fix: <action>.`

Required codes:
- `INVALID_START_FROM`
- `RESUME_BRIEF_MISSING`
- `RESUME_BRIEF_STALE`
- `RESUME_BRIEF_UNPARSEABLE`
- `RESUME_STATE_CONFLICT`
- `STATE_PHASE_AMBIGUOUS`
- `STATE_PHASE_UNRECOVERABLE`

### Continuation behavior

Once start phase is resolved:
- Continue through remaining phases in canonical order.
- Preserve all existing stop conditions and gates.
- Keep existing execute/QA loop behavior and optional security-review behavior.

### Breadcrumb observability

Minimum fields to write on `/auto` continuation:
- invocation mode
- requested start phase
- resolved start phase
- resolution source
- resolution status
- stop reason
- stop phase
- timestamp

Artifacts:
- append checkpoint in `docs/engineering/state.md`
- update `handoffs/resume_brief.md` when stopped before completion

## Consequences

Positive:
- Deterministic, auditable, and safer continuation.
- Better user control with explicit override.
- Clear implementation surface for `/sprint-plan`.

Tradeoffs:
- Slight increase in documentation and validation complexity.
- Requires active/template parity updates during implementation.

## Implementation Notes

- Scope remains workflow/process semantics only.
- No bypass of decision gates, pause policy, missing-input blockers, or loop caps.
- Preserve backward compatibility: manual teams unchanged unless `/auto`
  continuation is invoked.
