# DEC-0006: Critical Evaluation in Intake and Architecture

## Status: Accepted

## Context

The AI currently accepts all ideas passively during /intake and all design proposals during /architecture. Users want the AI to challenge weak ideas, check for duplicates, and suggest alternatives — acting as a constructive reviewer rather than a passive scribe.

## Options

### Option A: Add evaluation step to existing /intake and /architecture
Insert a step 0 in each command that evaluates before proceeding. Update PO and Tech Lead agent definitions with evaluation rules.

### Option B: Separate /evaluate command
A pre-intake command that evaluates an idea before running /intake. User runs /evaluate first, then /intake if approved.

### Option C: Separate /bug and /feature-request commands
Dedicated commands for different input types, each with built-in evaluation logic specific to its type.

## Decision

**Option A.** Keeping /intake as the single entry point avoids command sprawl and ensures every idea gets evaluated. Adding step 0 is minimally invasive — existing steps are unchanged, just shifted. The user's preference was explicitly for /intake as the unified entry point (no /bug or /feature-request).

The evaluation must be constructive, not blocking (AC-7). The user always has the final say.

## Consequences

- PO agent gets 4 new evaluation rules.
- Tech Lead agent gets 3 new challenge rules.
- /intake and /architecture commands each get 1 new step.
- Both active and template copies must be updated together.
- No new commands needed.
