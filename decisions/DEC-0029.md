# DEC-0029: Enforced Per-Phase Subagent Isolation with Auditable Evidence and Fail-Closed Gates

## Status

Accepted

## Context

Users reported that `/auto` flow was executed in one agent context instead of
fresh subagent contexts per phase. Existing policy (DEC-0007, US-0023) already
mandates phase isolation, but execution compliance can drift without
deterministic enforcement or blocking. US-0048 closes this gap by making
isolation a hard-enforced contract with auditable evidence and fail-closed
gates at workflow progression and release.

## Decision Drivers

- Prevent recurrence of single-context execution across phases.
- Provide auditable, machine-checkable evidence that each phase ran in a fresh
  subagent context.
- Block progression and release when evidence is missing or invalid (fail closed).
- Give operators explicit diagnostics (reason code, phase, evidence ref,
  remediation) — no silent block or vague error.
- Preserve deterministic pause/resume behavior with isolation provenance.

## Options Considered

### Option A: Advisory-only (deviation logging, no gates)

- **Pros**: Low effort; no blocking.
- **Cons**: Does not close recurrence risk; user asked for enforcement, not
  logging only. Rejected.

### Option B: Hard enforcement + auditable evidence + fail-closed gates (chosen)

- **Pros**: Closes compliance gap; deterministic detection and blocking;
  operator gets explicit diagnostics; aligns with PO recommendation and
  vision discovery notes for US-0048.
- **Cons**: Evidence write discipline required; possible friction if writes
  are inconsistent. Mitigated by clear schema, remediation guidance, and
  bounded migration for legacy artifacts.

## Decision

Adopt Option B:

1. **Isolation evidence schema**: Each phase transition writes mandatory
   evidence (phase_id, role, fresh_context_marker, timestamp, evidence_ref)
   to canonical locations (e.g. `docs/engineering/state.md` and/or append-only
   isolation log). Schema and canonical locations documented in runbook.

2. **Orchestrator contract**: `/auto` must not execute phase work in-process;
   must spawn/trigger fresh subagent context per phase and per execute↔QA
   cycle. Fail if phase work is executed without spawning fresh context.

3. **Execute/QA loop**: Each cycle (execute then QA) requires fresh-context
   semantics and deterministic evidence fields per cycle.

4. **Fail-closed gates**: Missing or invalid isolation evidence triggers
   deterministic reason codes (e.g. `PHASE_CONTEXT_ISOLATION_MISSING`,
   `PHASE_CONTEXT_ISOLATION_VIOLATION`, `ISOLATION_EVIDENCE_STALE`,
   `ISOLATION_EVIDENCE_INVALID`) and blocks progression. No silent continuation.

5. **Verify-work and release**: Both include an isolation-compliance gate that
   blocks finalization on unresolved isolation violations. Gate order at
   release: check-in test → QA → UAT → isolation compliance → release
   finalization.

6. **Pause/resume**: Resume checkpoints carry isolation provenance (e.g.
   evidence_ref at resume); continuation requires new context and new
   evidence for resumed and subsequent phases. Evidence survives pause/resume
   for gate checks.

7. **Active/template parity**: Command contracts, runbook, README, and
   regression coverage for isolation enforcement are aligned across active
   repo and `template/`.

## Consequences

### Positive

- Recurrence of single-context execution is blocked by gates.
- Auditable evidence supports compliance and debugging.
- Operators get explicit remediation instead of silent or vague failures.

### Negative

- Additional artifact writing and gate checks; possible friction if evidence
  writing is inconsistent. Mitigated by clear schema and remediation.

### Neutral / Follow-up

- Implementation will define exact canonical evidence locations and any
  migration/legacy handling for pre-US-0048 sprints (see architecture and
  sprint plan).
