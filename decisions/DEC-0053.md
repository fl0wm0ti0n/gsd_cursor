# DEC-0053: User-visible internal metadata sanitization guard

- Date: 2026-03-21
- Status: Accepted
- Story: `US-0071`
- Research refs: `R-0046`
- Related: `DEC-0040` (artifact ordering for evidence), `DEC-0029` / `DEC-0038`
  (isolation + strict-proof evidence in workflow outputs), `DEC-0043`
  (architecture history preservation)

## Context

Planning identifiers (`US-xxxx`, `DEC-xxxx`, `R-xxxx`) routinely appear in
internal documentation and code comments. They must not leak into
**user-visible software outputs** (CLI stdout/stderr, UI copy, error strings
surfaced to operators or end users, installer-visible text), which creates
noise, breaks immersion, and can disclose internal process metadata (CWE-209
class information exposure in messages).

Prior contracts did not define a single deterministic deny/allow boundary
across execute, QA, and release evidence.

## Decision

Adopt a **deterministic two-layer policy**:

1. **Forbidden pattern baseline (deny in disallowed channels)**  
   In user-visible software surfaces only, treat these as **forbidden
   planning-shaped tokens** (regex-level contract, tune to reduce false
   positives):
   - `US-[0-9]{4}`
   - `DEC-[0-9]{4}`
   - `R-[0-9]{4}`

2. **Explicit allowlist (internal-only homes)**  
   The same tokens remain **permitted** in:
   - `docs/**` (including engineering/product artifacts),
   - `.cursor/**` (commands, rules, agents),
   - sprint, handoff, and decision artifacts (for example `sprints/**`,
     `handoffs/**`, `decisions/**`),
   - **code comments** in source files (line/block comments as defined by the
     stack; string literals that render to users are **not** comments).

Channel classification follows discovery refinements in `US-0071`: misclassifying
a path must fail closed in QA with a deterministic diagnostic, not silent pass.

### Enforcement boundaries

- **`/execute`**: non-bypass **default guard** for in-scope changes—before
  completing dev work, scanning or equivalent must ensure no new forbidden
  tokens appear in user-visible output targets (exact file globs and command
  hooks are implementation details in execute/QA; architecture requires the
  guard to be mandatory, not advisory).
- **`/qa`**: automated verification with **fail-closed** behavior; on
  detection, emit deterministic reason code, file/path evidence, token class,
  and safe remediation (replace with neutral operator-facing text or indirect
  reference).
- **Release/readiness**: artifacts must attest checks **ran and passed** (not
  only that policy prose exists).

### Reason-code vocabulary (minimum)

Document and reuse consistently in execute, QA, and release evidence:

- `USER_VISIBLE_INTERNAL_METADATA_DETECTED` — forbidden token matched in a
  disallowed channel.
- `METADATA_SANITIZATION_POLICY_MISSING` — required policy text, guard hook, or
  check entrypoint absent when mandatory for the story scope.
- `METADATA_SANITIZATION_SCOPE_AMBIGUOUS` — cannot classify path as allowlisted
  vs user-visible (fail closed; fix classification table).

Implementations may add **narrow** subcodes only if they remain deterministic and
mapped in runbook/command guidance.

### Parity and regression

- **Active/template parity** for policy-bearing commands, rules, runbook, and
  README (`US-0071` AC-8).
- **Regression**: positive (clean outputs), negative (injected leak blocked),
  allowlist (docs/comments untouched), idempotent reruns.

## Consequences

- **Positive**: Single auditable boundary; aligns with secure messaging
  practice; traceable via shared reason codes.
- **Negative**: Tight regexes can false-positive on unrelated strings; mitigated
  by planning-shaped patterns and path-scoped scanning.
- **Neutral**: Internal traceability in docs and comments unchanged.
